【一、测试环境与兼容边界】

记录日期：2026-09-05。固件来自只读设备查询，应用版本/验收来自此前测试窗口。
A：一加 13 / PJZ110，Android 16 / API 36 / arm64-v8a；
   PJZ110_16.0.10.501(CN01)，ColorOS 属性 ro.build.version.oplusrom=V16.1.0。
B：一加 11 / PHB110，Android 16 / API 36 / arm64-v8a；
   PHB110_16.0.2.400(CN01)，ColorOS 属性 ro.build.version.oplusrom=V16.0.0。
Server：Linux x86_64，physical 模式，1.4.1 CI 分发 musl 二进制。
Mask 历史实测：LSPosed 2.2.0 / libxposed API 102。

A 有原生 StrongBox 实现，原生 StrongBox + Android RKP 曾单独验证；
当前远程验收关闭该后端并启用 Mask，StrongBox 功能查询 false、app_attest_key=true。
B 当前固件 StrongBox 查询 false，历史 profile strongbox=false；
实测为默认 TEE KeyMint + native relay，没有“双端 StrongBox 均通过”的证据。
B app_attest_key 查询 true。能力声明、真实 HAL 存在、具体算法可用是不同概念。

远程验收配置：
  remote=true，local_hw=false，disable_native_strongbox=true，
  use_native_strongbox=false，应用 GlobalDefault，A 启用 Mask。
历史应用版本：
  Integrity Checker 2.2；Paytm 10.83.12；GMS 26.34.31；Play 商店 52.9.21-34。
三绿曾通过；Paytm 曾进入手机号输入页并保持，也曾间歇报 00000。
重启改善不能证明误报或永久修复，未因此验证支付/绑卡等其他业务。

A 安装器和 Mask 最低 API 29 只是安装门槛，不是 Android 10+ 全兼容承诺。
Ommega 实际依赖 keystore2、KeyMint AIDL、root 注入与固件接口；CI 模块为 arm64-v8a。
其他 ROM、系统版本、root 管理器、架构、B StrongBox 和算法组合需单独验证。
不能保证所有设备、应用或网络环境可用。不要把检测器结果当作安全认证。

【二、系统结构与 1.4.1 边界】

A 接管 target.txt 中应用的 Keystore 请求，经 Server 访问 B。
B native relay 处理 profile / attest / sign / decrypt / agree。
Server 负责鉴权、调度、设备状态与管理；B-app 仅是可选 Android 客户端，
只支持 attest/sign/decrypt，缺少 profile/agree，使用 B-app 自身 AndroidKeyStore
身份，不能替代 native B 完成同一验收。

remote-only 不等于所有操作在 B 执行：远程开启、有 attestation challenge、
且未提供调用方 attestation key 时，软件 TA 才进入远程生成路径。
其他生成可在 A 完成；远程密钥的签名、解密、协商由 B 完成。
A 负责应用认证检查和本地状态。B 转换 NO_AUTH_REQUIRED、ATTEST_KEY → SIGN，
不能描述成 B 硬件验证了 A 用户的认证令牌。

相对上游的主要改动：
  - A 启动前取得并冻结 B 真实 profile，网络未就绪会重试。
  - Server 允许空 keymint_author，拒绝缺失、非字符串和纯空白。
  - A 检查 profile 与叶证书 challenge、App ID、版本、安全级别。
    完整可信根、逐级签名和撤销验证未完成；Server 非空链检查不是密码学验证。
  - A 原生 StrongBox/RKP、三档应用策略、WebUI 实时配置与冷启动事件重放。
  - B SPL 管理、relay 连接热加载、持久化 keyblob upgradeKey 与队列竞态修复。
  - 真实 HAL 错误可经 keymint_error_code 传递；未知错误保持通用失败，
    不解析错误字符串猜测 HAL 代码，也不新增本地回退。
  - NoPadding/SHA-224/NONE/OAEP MGF 定向修复与远程 AGREE_KEY。
  - 前六批验证覆盖 P-256/P-384/P-521/X25519 协商、签名/解密、
    A 重启前后认证密钥生命周期；第六批 A Android workspace 516 项测试通过。
  - Wrapped import 未纳入支持验收，其余未完成工作不冒充已完成。
CI 成功、历史实机验证与最终安装包应用验收需分别看待。

【三、构建产物与版本】

ommega-1.4.1 aggregate artifact 解压后为平铺文件：
  ommega-a-release-arm64-v8a-1.4.1-<commit>.zip
  ommegaclient-b-release-arm64-v8a-1.4.1-<commit>.zip
  relay_rs-linux-x86_64-musl
  Ommega-B-app-1.4.1-debug-signed.apk
  StrongBoxCapabilityMask-1.4.1-debug-signed.apk
  SHA256SUMS
  build-info.json

外层 artifact 可解压，A/B 安装 ZIP 保持完整；部署前核对哈希及源提交。
两个 APK 均使用 Android 默认 debug 签名。CI 缓存复用该身份，但缓存失效可能改变签名，
并非正式发布签名；私钥不分发。签名不同的已安装 APK 不能直接覆盖，不要盲目卸载清数据。

CI 并行构建 A/B/Server/APK；固定 nightly-2026-09-01、提交 Cargo.lock、
缓存 Rust/Gradle，并保留 workspace、Server、B ELF、WebUI、版本同步与 Mask 测试。
默认沿用源码版本，不自动加版本或提交；手动 release_version 仅覆盖该次构建。
当前仅忽略纯 Markdown 改动，TXT 修改仍触发 CI。

【四、Server 部署】

在二进制工作目录创建 .env（环境变量优先）：
  RELAY_BIND=0.0.0.0
  RELAY_HTTP_PORT=10886
  RELAY_HTTPS_PORT=8443
  RELAY_USE_TLS=true
  RELAY_TLS_CERTFILE=data/tls/server.crt
  RELAY_TLS_KEYFILE=data/tls/server.key
  RELAY_TOKEN=<random-static-token>
  RELAY_ADMIN_USER=admin
  RELAY_ADMIN_PASSWORD=<strong-password>
  RELAY_ATTEST_SOURCE=physical
  # RELAY_MYSQL_URL=mysql://user:password@127.0.0.1:3306/ommega
  # RELAY_SECRET_KEY=<random-secret>

启动：
  chmod 0755 relay_rs-linux-x86_64-musl
  ./relay_rs-linux-x86_64-musl

入口：/api/health/、/status/、/jiyin004/（后台）、/login/。
缺少 TLS 证书时会回退仅 HTTP，不应误认为仍受 HTTPS 保护。
无 MySQL 时可使用静态 Token 进行物理转发；后台 Token、数据库 keybox、支付及持久化
功能受限。启用数据库后可分配 A/B 角色 Token。.env.pay.example 不是完整配置模板。

更新：确认无 pending/assigned 任务，上传独立临时文件，校验 SHA-256，
备份旧程序，再停该服务、原子替换并恢复权限、启动并核对运行映像、健康与 B 重连。
启动失败恢复已校验备份。重启会清空内存任务统计，failed=0 不代表旧错误已修复。
不要直接覆盖正在运行的程序。验收通过正常 A 应用路径进行，避免中断在途操作。

【五、B 模块、Relay WebUI 与 SPL】

安装 B ZIP 后，在 WebUI「Relay 配置」或 /data/adb/ommega/relay.conf 填写：
  OMMEGA_RELAY_SERVER=https://<server>:8443
  OMMEGA_RELAY_DEVICE_ID=<b-device-id>
  OMMEGA_RELAY_MACHINE_ID=
  OMMEGA_RELAY_TOKEN=<b-token-or-static-token>
  OMMEGA_RELAY_LOG_ENABLED=true
  OMMEGA_RELAY_LOG_LEVEL=debug
  OMMEGA_RELAY_LOGCAT_ENABLED=true
  OMMEGA_RELAY_LOGCAT_LEVEL=info

设备 ID 与 A 一致；角色 Token 使用 B 角色。B 当前接受无效 TLS 证书，
仅使用 HTTPS 不等于认证了服务器身份，部署者需保护网络与凭据。

WebUI 支持以上八项、Token 隐藏/显示、校验及冲突检测，保存前保留 .webui.bak，
保留注释及未知字段并原子写入。连接参数热加载；四项日志设置下次启动才生效。
  touch /data/adb/ommega/restart.all
只请求重新读取连接配置，不重启 relay/设备、不初始化日志、不应用 SPL。
文件日志：/data/adb/ommega/logs/relay.log；logcat tag：ommegaclient-b。

SPL 位于独立折叠面板：System/Boot/Vendor，格式 YYYY-MM-DD。
保存写 /data/adb/ommega/spl.conf；属性变化时重载原生 KeyMint 和 keystore2。
留空选择首次记录的 spl-baseline.conf；这不一定是安全恢复值！
较高 SPL 可使 keyblob 升级并绑定该值，降回旧值可能导致密钥或凭据数据无法使用。
属性查询不能证明硬件接受，需在允许的正常应用路径用新证明核对。

模块生命周期入口：
  sh /data/adb/modules/ommegaclient_b/service.sh
这是服务级操作，会清理精确路径的旧 relay、重新应用 SPL 并启动 relay，
不是普通配置保存步骤。仅在已解锁、无在途 TEE 调用、已核对有效 SPL、
有无需硬重启的恢复路径且已明确允许时使用。不要在 TEE 调用中杀进程或强制超时。
本项目主 B 绝对禁止硬重启，不能以通用安装/升级提示解除该限制。
软重启也须单独评估，不能用 Android stop/start 或盲杀代替设计好的生命周期。
不要将 SPL 修改和重启组合操作，不要删除凭据/Keystore 数据库作为修复。

【六、A 模块与路由】

安装 A ZIP 后按管理器要求加载。连接配置 /data/adb/ommega/config 示例：
  url: https://<server>:8443
  device_id: <b-device-id>
  token: <a-token-or-static-token>
  remote: true
  local_hw: false
  tls_insecure: true
  debug_logging: false
  disable_native_strongbox: false

这是格式示例，不是第一节测试配置的完整复刻。
tls_insecure=true 跳过 A 的证书验证；有可信证书时按实际环境设置。
remote 与 local_hw 独立；角色 Token 使用 A 角色。

目标列表：/data/misc/keystore/ommega/target.txt，每行普通包名，不加 !/?。
策略文件：/data/misc/keystore/ommega/target-security.toml。
WebUI 长按已选应用：
  全局默认：遵循全局与能力。
  StrongBox：显式选择，覆盖全局禁用。
  TEE：将安全级别请求改为 TEE，包括显式 StrongBox。
未选择的应用仍走系统路径。旧 strongbox_unavailable_packages 仅在新策略文件不存在时迁移。

disable_native_strongbox 默认 false，只影响 GlobalDefault 目标：
开启时显式 StrongBox 请求返回 HARDWARE_TYPE_UNAVAILABLE(-68)，
应用是否自行回退取决于应用，不能承诺“必定降级成功”。

/data/misc/keystore/ommega/config.toml：
  [main]
  use_native_strongbox = true
选择 A 原生 StrongBox/RKP；TEE 仍可远程。修改后：
  touch /data/adb/ommega/restart.keymint
仅回收 Ommega keymint 子进程，不重启设备。

target、策略、远程连接及普通配置实时读取。WebUI Hash/Boot Key/SPL 同步到 [trust]；
SPL 更新运行 TA，Hash/Key 必要时回收 Ommega keymint 并等待 RPC。
日志：/data/misc/keystore/ommega/logs/keymint.log、injector.log。
模块卡片与 keystore2 maps 中 ommega-inject 可辅助检查，不能代替实机请求验收。

【七、StrongBoxCapabilityMask APK】

用途：可选 A 端 libxposed 模块，让按系统功能表选择路径的应用看到“未声明 StrongBox”。
无该功能声明的设备通常不需要；测试 B 不需要。不是 Paytm/完整性检测通用修复。

实现：仅 system_server，启动时 hook
com.android.server.SystemConfig.getAvailableFeatures()，
删除 android.hardware.strongbox_keystore，保留 android.hardware.keystore.app_attest_key。
全局生效，包括 Ommega 未选中的应用；无分包名功能、不注入目标 App。

兼容条件：API 29 安装门槛，框架支持 libxposed API 102，
ROM 保留 AOSP 的该方法、可修改 Map 和功能发布/缓存路径，没有厂商旁路或硬编码结果。
“遵循 AOSP”不是认证或全版本保证，目前实机仅第一节 A 环境。
Android 16 的进程功能缓存说明见 README 中 AOSP 源码链接。

使用：
  1. 在 A 安装 StrongBoxCapabilityMask-1.4.1-debug-signed.apk。
  2. LSPosed 启用，静态作用域仅 system（系统框架），不要勾应用。
  3. 在允许正常重启的 A 上重启并解锁；仅退出 App 无法重建系统功能表。
  4. 检查：
       pm has-feature android.hardware.strongbox_keystore
       pm has-feature android.hardware.keystore.app_attest_key
       logcat -d -s StrongBoxCapabilityMask
     预期 false、原有 app_attest_key 保持 true，日志 hook_registered/feature_removed。
     必要时使用正常测试 App 核对应用进程缓存，shell 结果不能冒充所有调用路径的证据。
  5. 撤销：LSPosed 禁用后重启 A。升级先核对 APK 签名。
禁止将该重启步骤应用到禁止硬重启的 B。

模块不改系统 XML，不停止 StrongBox HAL，不删除/迁移已有密钥，不改变真实
Bootloader 证明状态，也不阻止直接 StrongBox 请求。HAL running 与 Mask 生效不矛盾。
原生硬件证明仍可能暴露解锁状态，TEE 证明也有相应字段；feature=false 不代表已隐藏。

后果：应用可能降级、拒绝运行、丢失 StrongBox 相关功能或改变分发行为，
也可能识别声明/接口不一致。旧密钥不会自动转换；是否继续使用由应用决定。
系统进程 hook 可能引发兼容性、崩溃或启动异常。
本项目及 Mask 按现状提供，不保证适用性、安全性或检测结果；使用者自担风险。
对数据丢失、设备异常、账户限制、业务或财产损失概不负责（适用法律允许范围内）。
不接受风险请勿使用。

五类控制须区分：
  use_native_strongbox：A 后端；禁用开关：GlobalDefault 路由；
  每应用 StrongBox/TEE：显式路由；Mask：全局功能声明；
  Server StrongBox 强健模式：B 能力类错误后同设备重试 TEE，默认关闭且重启复位。
A 原生请求不经过 B 重试路径，Server 开关不能代替 A 配置。

【八、验收、排障与备份】

顺序：Server health → B 在线 → 正常 A 应用 profile/新证明 → 必要的签名/解密/协商。
三绿与 Paytm 手机号页是本次人工验收标准，不要求清数据，也不代表后续业务均可用。
不要在主 B 上运行直接 HAL 矩阵、故障注入或中断真实 TEE 调用。

常见问题：
  Network is unreachable：先看后续 profile 重试是否恢复。
  invalid profile result shape：核对三端协议；空 author 合法，缺失/非字符串/纯空白不合法。
  relay.lock 占用：只读核对精确进程路径，满足第五节条件后再走生命周期，勿盲杀。
  -74：ATTESTATION_KEYS_NOT_PROVISIONED，检查 RKP 实例/rkpd/证书池，不能当作无硬件。
  user 0 super keys：检查解锁事件重放/RPC 与授权生命周期，不要清系统凭据。
  no key for alias：核对原设备和持久化会话，不能用重启清空队列冒充修复。
  Paytm 00000：保存时间对齐日志，不能只凭字符串判断 Mask 或 KeyMint；
              不使用 Frida 作为常规验收观测，已知该应用会对其反应。

更新前备份 A /data/misc/keystore/ommega/、B 的配置与持久化密钥会话数据、
Server .env/数据库/当前二进制。密钥与设备绑定，备份不保证可跨设备恢复。
同协议小改可只更新对应端，协议/profile 变更先核对三端兼容。
不要提交 Token、密码、私钥、真实服务地址或设备敏感数据。
