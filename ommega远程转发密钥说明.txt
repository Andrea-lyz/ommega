============================================================
  Ommega 1.4.0 远程 KeyMint 使用说明（Andrea-lyz Fork）
============================================================

上游仓库：
  https://github.com/jiyin004-jpg/ommega

本 Fork：
  https://github.com/Andrea-lyz/ommega

说明：
  1. 本 Fork 不是上游官方发行版或官方在线服务。
  2. 当前版本为 1.4.0，模块作者为 jiyin004, Andrea-lyz。
  3. 本文不提供公共服务器地址或 Token。所有凭据必须由部署者自行生成。
  4. A/B 端要求 Android 12+、arm64-v8a；B 端越狱设备禁止硬重启时，
     可使用模块 service.sh 或系统提供的软重启方式。


【一、系统结构】

  A 端：
    拦截 target.txt 中应用的 Android Keystore 请求。
    TEE 请求可经 Server 转发给 B 端；StrongBox 可选择 A 端原生 HAL。

  B 端：
    连接 Server，领取 profile、attest、sign、decrypt 任务，
    使用本机真实硬件 KeyMint 执行后回传。

  Server：
    负责鉴权、A/B 任务调度、设备在线状态、任务队列和管理后台。

基本链路：

  A 端应用
    → keystore2 中的 Ommega 注入器
    → A 端 keymint
    → Server
    → B 端真实硬件 TEE
    → Server
    → A 端返回结果


【二、1.4.0 相比上游 1.3.0 的主要改动】

  1. B 端新增真实 KeyMint profile：
     - Stable AIDL interface version/hash
     - canonical profile version
     - getHardwareInfo() 硬件版本
     - security level
     - keymint_name/keymint_author
     - StrongBox 可用性

  2. A 端启动时取得并冻结 B 端 profile：
     - 网络尚未就绪时等待并重试
     - 证明结果必须与已冻结 profile 一致
     - profile 或证书链不一致时默认失败关闭

  3. 原生 StrongBox + Android RKP：
     - use_native_strongbox=true 时使用 A 端真实 StrongBox HAL
     - StrongBox 证明密钥从 Android RKP strongbox 实例获取
     - TEE 路径仍可转发到 B 端

  4. A 端每应用安全级别：
     - 全局默认
     - StrongBox
     - TEE
     策略保存在 target-security.toml，保存后实时生效。

  5. A 端“禁用原生 StrongBox”总开关：
     - 默认关闭
     - 只影响 target.txt 中选择“全局默认”的应用
     - 显式 StrongBox 或 TEE 选择优先

  6. A 端 WebUI 实时配置：
     - 远程地址、Token、设备 ID、TLS、日志立即生效
     - Hash、Boot Key、System/Vendor/Boot SPL 保存后立即应用
     - 必要时只重启 Ommega keymint，不重启整台设备
     - UTF-8 Base64 安全写入配置，避免 shell heredoc 注入

  7. keystore2 冷启动生命周期修复：
     - Binder hook 先安装，RPC 在后台 warm-up
     - OnDeviceUnlocked、auth token、用户维护事件排队并重放
     - 修复 user 0 super key 未初始化导致的生物认证绑定密钥失败

  8. B 端 SPL WebUI：
     - 自定义 System / Boot / Vendor SPL
     - 保存即应用
     - 只软重载 KeyMint 与 keystore2
     - service.sh 在后续模块加载或软重启时重新应用
     - 不依赖 post-fs-data.sh，不请求硬重启

  9. B 端 relay 与 Server：
     - relay.conf 运行时热加载
     - 长轮询与 TEE worker 分离
     - 修复 wait/result、超时、重复请求、掉线回收等队列竞态
     - Server 校验任务归属、证书链、profile 和安全级别
     - Server StrongBox 强健模式与 A 端 StrongBox 控制彻底分离

  10. CI：
      - A/B Android workspace 检查
      - Server Clippy 与单元测试
      - A/B 模块、Linux musl Server、B-app APK 构建
      - B 端 ELF 链接检查
      - 统一 1.4.0 artifact


【三、构建产物】

GitHub Actions 的 ommega-1.4.0 artifact 包含：

  a-side/source/target/
    ommega-a-release-arm64-v8a-1.4.0-<commit>.zip

  b-side/source/target/
    ommegaclient-b-release-arm64-v8a-1.4.0-<commit>.zip

  b-app/source/dist/
    app-release.apk

  server/source/dist/
    relay_rs-linux-x86_64-musl

每次部署前都应核对构件 SHA-256，不要仅根据文件名判断版本。


【四、Server 部署】

4.1 最小环境要求

  - Linux x86_64
  - 公网或 A/B 均可访问的内网地址
  - 默认 HTTP 端口 10886
  - 默认 HTTPS 端口 8443
  - musl 构件为静态链接二进制

4.2 最小 .env 示例

  RELAY_BIND=0.0.0.0
  RELAY_HTTP_PORT=10886
  RELAY_HTTPS_PORT=8443
  RELAY_USE_TLS=true
  RELAY_TLS_CERTFILE=data/tls/server.crt
  RELAY_TLS_KEYFILE=data/tls/server.key

  RELAY_TOKEN=改成随机静态Token
  RELAY_ADMIN_USER=admin
  RELAY_ADMIN_PASSWORD=改成强密码

  RELAY_ATTEST_SOURCE=physical

  # 可选数据库
  # RELAY_MYSQL_URL=mysql://user:password@127.0.0.1:3306/ommega
  # RELAY_SECRET_KEY=改成随机服务端密钥

说明：
  - 环境变量优先于 .env。
  - 未配置 TLS 证书时自动退回为仅 HTTP。
  - 未配置 MySQL 时，物理 A/B 转发仍可使用静态 RELAY_TOKEN；
    Token 管理、数据库 keybox、支付和持久化记录等功能受限。
  - 配置 MySQL 后，可从后台为 A/B 分别生成带角色的 Token。
  - server/source/.env.pay.example 只包含支付网关示例，不是完整 Server 配置。

4.3 启动与入口

  chmod 0755 relay_rs-linux-x86_64-musl
  ./relay_rs-linux-x86_64-musl

  健康检查：
    http://<server>:10886/api/health/

  公开设备状态：
    http://<server>:10886/status/

  管理后台：
    http://<server>:10886/jiyin004/

  登录页：
    http://<server>:10886/login/

  登录账号和密码来自：
    RELAY_ADMIN_USER
    RELAY_ADMIN_PASSWORD

4.4 安全更新 Server

  1. 上传为临时文件，例如 relay.next。
  2. 核对本地和服务器端 SHA-256 完全一致。
  3. 备份当前 relay_rs。
  4. 停止 systemd 服务。
  5. 原子替换二进制并恢复权限。
  6. 启动服务。
  7. 检查 /api/health/、监听端口、B 端重连和 failed 队列。
  8. 从 A 端实际请求一次 /api/profile/。

不要直接覆盖正在执行的二进制，也不要在未备份时更新。


【五、B 端模块部署】

5.1 安装

  安装：
    ommegaclient-b-release-arm64-v8a-1.4.0-<commit>.zip

  首次加载后配置：
    /data/adb/ommega/relay.conf

5.2 relay.conf 示例

  OMMEGA_RELAY_SERVER=https://<server>:8443
  OMMEGA_RELAY_DEVICE_ID=<b-device-id>
  OMMEGA_RELAY_MACHINE_ID=
  OMMEGA_RELAY_TOKEN=<b-token-or-static-token>

  OMMEGA_RELAY_LOG_ENABLED=true
  OMMEGA_RELAY_LOG_LEVEL=debug
  OMMEGA_RELAY_LOGCAT_ENABLED=true
  OMMEGA_RELAY_LOGCAT_LEVEL=info

要求：
  - OMMEGA_RELAY_DEVICE_ID 必须与 A 端 device_id 完全一致。
  - 使用角色 Token 时必须使用 B 角色 Token。
  - 自签名 HTTPS 由客户端按当前实现接受；正式部署仍建议使用可信证书。

5.3 配置生效

保存 relay.conf 后 relay 会自动热加载，不需要重启设备。

需要主动触发读取时：

  touch /data/adb/ommega/restart.all

需要重新启动 B 端 relay 时：

  sh /data/adb/modules/ommegaclient_b/service.sh

service.sh 会精确清理旧模块进程、释放 relay.lock、重新应用 SPL 后启动 relay。
它不会请求硬重启。

5.4 B 端 SPL WebUI

KernelSU/APatch 模块 WebUI 提供：

  System SPL
  Boot SPL
  Vendor SPL

格式：
  YYYY-MM-DD

保存：
  写入 /data/adb/ommega/spl.conf，立即应用；
  属性变化时软重载原生 KeyMint 和 keystore2。

留空：
  恢复模块首次记录的基线值。

注意：
  Android 属性显示已修改，不代表硬件 TEE 已接受。
  必须重新生成证明证书并核对 osPatchLevel、vendorPatchLevel、
  bootPatchLevel。

5.5 B 端日志

  文件：
    /data/adb/ommega/logs/relay.log

  logcat tag：
    ommegaclient-b

  Server /api/health/ 中应显示该 device_id 在线。


【六、A 端模块部署】

6.1 安装

  安装：
    ommega-a-release-arm64-v8a-1.4.0-<commit>.zip

  安装或升级模块代码后，应按模块管理器要求重新加载一次。
  之后普通配置保存不需要重启设备。

6.2 远程配置

在 KernelSU/APatch WebUI 或下列文件中设置：

  /data/adb/ommega/config

示例：

  url: https://<server>:8443
  device_id: <b-device-id>
  token: <a-token-or-static-token>
  remote: true
  local_hw: false
  tls_insecure: true
  debug_logging: false
  disable_native_strongbox: false

说明：
  - device_id 必须与 B 端一致。
  - 使用角色 Token 时必须使用 A 角色 Token。
  - remote=true 才会启用远程 TEE。
  - local_hw 与远程模式是独立配置，不要用它代替 remote。
  - disable_native_strongbox 默认关闭。

6.3 目标应用

  包名列表：
    /data/misc/keystore/ommega/target.txt

  安全级别策略：
    /data/misc/keystore/ommega/target-security.toml

target.txt 每行只写一个普通包名，不再使用 ! 或 ? 后缀。

WebUI 长按已勾选应用可选择：
  - 全局默认
  - StrongBox
  - TEE

未加入 target.txt 的应用继续走系统原始 Keystore。

6.4 “禁用原生 StrongBox”

该开关独立于每应用模式：

  关闭：
    全局默认应用按设备正常能力运行。

  开启：
    全局默认应用按原生 StrongBox 不可用处理，从而走 TEE 降级。

  显式 StrongBox：
    覆盖全局禁用。

  显式 TEE：
    始终使用 TEE。

6.5 use_native_strongbox

位置：
  /data/misc/keystore/ommega/config.toml

设置：

  [main]
  use_native_strongbox = true

作用：
  - StrongBox 安全级别使用 A 端真实 StrongBox HAL 和 Android RKP。
  - TEE 仍走 B 端远程链路。

生效：

  touch /data/adb/ommega/restart.keymint

只重启 Ommega keymint 子进程，不需要重启整台设备。

6.6 Hash、Key、SPL

A 端 WebUI 设置 Verified Boot Hash、Verified Boot Key、安全补丁后：

  - 配置同步到 webui-props.sh 和 config.toml [trust]
  - SPL 直接更新运行中的 TA
  - Hash/Key 变化时只回收 Ommega keymint 并等待 RPC 恢复
  - 不需要重启设备

6.7 A 端日志与进程

  KeyMint 日志：
    /data/misc/keystore/ommega/logs/keymint.log

  Injector 日志：
    /data/misc/keystore/ommega/logs/injector.log

  运行状态：
    模块卡片应显示“运行中”。

  注入确认：
    keystore2 的 /proc/<pid>/maps 中应包含 ommega-inject。


【七、StrongBox 四层控制不要混淆】

  1. use_native_strongbox
     生效位置：A 端 KeyMint 后端
     含义：使用 A 设备真实 StrongBox/RKP

  2. 禁用原生 StrongBox
     生效位置：A 端全局默认目标应用
     含义：让这些应用认为原生 StrongBox 不可用

  3. 每应用 StrongBox / TEE
     生效位置：A 端应用路由
     含义：覆盖全局默认行为

  4. Server StrongBox 强健模式
     生效位置：B 端 StrongBox 任务已经返回能力类错误之后
     含义：在同一 B 端重试 TEE
     默认：关闭
     持久化：仅内存，Server 重启后恢复关闭

当 A 端使用真实原生 StrongBox 时，该请求通常不会到达 Server 的 B 端
StrongBox 降级阶段，因此 Server 强健模式不能代替 use_native_strongbox。


【八、串联验证】

按以下顺序验证：

  1. Server：
     /api/health/ 返回 status=ok。

  2. B 端：
     /api/health/ 的 connected_devices 中出现 B device_id。

  3. A → B profile：
     从 A 端请求 /api/profile/，必须返回 HTTP 200。
     当前已验证真实 B HAL 可返回：
       keymint_name = "Keymint HAL: 4"
       keymint_author = ""
     1.4.0 Server 接受空 author，但仍拒绝字段缺失、非字符串和纯空白值。

  4. 证明：
     A 端目标应用生成一次新证明；
     Server 任务完成，B 日志出现处理结果；
     A 日志中的 remote profile 与 B 保持一致。

  5. StrongBox：
     use_native_strongbox=true 时检查 A 日志是否显示使用原生 StrongBox，
     并确认 Android RKP 取钥成功。

  6. 用户认证绑定密钥：
     检查 OnDeviceUnlocked 是否在 RPC 就绪后成功重放，
     再验证需要强生物认证的 AndroidKeyStore 密钥创建与读取。


【九、常见问题】

Q：开机时出现 Network is unreachable？
A：网络早于 Wi-Fi/移动网络启动时属于暂态。1.4.0 会重试 remote profile。
   重点确认后续是否出现 identity_profile 成功记录。

Q：Server 返回 invalid profile result shape？
A：先确认 A/B/Server 是否来自兼容版本。1.4.0 允许 keymint_author=""，
   但不允许字段缺失、数字/null 或纯空白字符串。

Q：B 端提示 another relay instance is running 或 relay.lock 被占用？
A：不要按进程名盲杀，也不要直接覆盖运行中的二进制。执行 B 模块
   service.sh，让脚本按精确模块路径清理旧进程并释放锁。

Q：StrongBox 返回 -74？
A：-74 是 ATTESTATION_KEYS_NOT_PROVISIONED，不等于没有 StrongBox 硬件。
   检查 Android RKP strongbox 实例、rkpd 服务和证书池。

Q：强生物认证密钥重启后失败，提示 user 0 没有 super keys？
A：这是 keystore 授权生命周期问题，不是 StrongBox 包排除问题。
   检查 OnDeviceUnlocked 排队/重放和 RPC warm-up。

Q：A 端修改 target 或 StrongBox 策略后是否要重启？
A：不需要。target.txt、target-security.toml 和全局禁用开关实时读取。

Q：A 端修改 use_native_strongbox 后是否要重启整机？
A：不需要，但必须 touch restart.keymint 让 KeyMint 后端重新创建。

Q：B 端修改 SPL 后是否要硬重启？
A：不需要。WebUI 保存会立即应用并软重载 KeyMint/keystore2；
   service.sh 会在后续软生命周期中重新应用。


【十、升级边界】

  只修改 A 端 WebUI、注入器或 KeyMint：
    只需更新 A 模块。

  只修改 B 端 relay、SPL 控制或 service.sh：
    只需更新 B 模块。

  只修改 Server：
    只需安全更新 Server，A/B 不需要重刷。

  修改三端协议或 profile 字段：
    必须核对 A/B/Server 兼容性，再决定需要更新哪些端。

升级前应备份：
  - A /data/misc/keystore/ommega/
  - B /data/adb/ommega/relay.conf
  - B /data/adb/ommega/spl.conf
  - Server .env、数据库和当前二进制

不要把 Token、管理员密码、私钥或设备敏感数据提交到 Git。
